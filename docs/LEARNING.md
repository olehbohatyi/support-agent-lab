## B-01 (OLE-41). Bootstrap репозитория

### Что сделано и почему так

- **uv + `pyproject.toml` + `uv.lock`.** uv заменяет pip, venv и pyenv одним инструментом: сам ставит нужный Python (3.14), создаёт `.venv`, резолвит зависимости. `pyproject.toml` хранит минимальные версии (последние стабильные на момент bootstrap), `uv.lock` фиксирует точный набор, поэтому у всех и в CI одинаковое окружение.
- **Последние стабильные версии.** Python 3.14, Django 6.1, DRF 3.18, PostgreSQL 19. Решение записано в `docs/DECISIONS.md` (ADR-001).
- **Структура `config/` + `apps/<name>/`.** `config` — это настройки и корневые urls, а не приложение. Каждое приложение в `apps/` отвечает за одну область: tenants, knowledge, crm_mock, conversations, agent, evals. В `apps.py` указано `name = "apps.<name>"`, иначе Django не найдёт приложение по полному пути.
- **Настройки только из окружения.** `settings.py` читает переменные окружения, а `python-dotenv` подхватывает `.env` локально (`override=False`, поэтому реальные переменные окружения важнее). Без `DJANGO_SECRET_KEY` при `DEBUG=false` приложение падает при старте: лучше упасть сразу, чем работать с дефолтным ключом.
- **Postgres в docker compose, тесты на реальном Postgres.** На SQLite не работает full-text search, который понадобится в B-07. `django.contrib.postgres` подключён заранее. У сервиса есть `healthcheck`, поэтому `docker compose up -d --wait` ждёт готовности базы.
- **API закрыт по умолчанию.** В DRF нет классов аутентификации и стоит `IsAuthenticated`: любой эндпоинт до B-06 вернёт 401/403. Так ни одна ручка не окажется случайно публичной.
- **`/health/`** делает `SELECT 1`: это одновременно liveness и проверка базы. Первый тест проверяет, что Django, Postgres и pytest-django работают вместе.
- **ruff** — линтер и форматтер в одном. Правила `DJ` (Django), `B` (bugbear), `UP` (современный синтаксис), `I` (сортировка импортов).

### 3 вопроса интервьюера

1. **Почему тесты на Postgres, а не на SQLite? Это же медленнее.**
   Потому что я использую возможности Postgres (FTS, позже constraints), и тест на другой базе проверял бы не тот код. pytest-django создаёт тестовую базу один раз и откатывает каждую транзакцию, так что на этом объёме это быстро (около секунды).
2. **Как у вас устроены секреты?**
   Только переменные окружения. `.env` в `.gitignore`, а `.env.example` без значений лежит в репозитории как контракт. Без секретного ключа в не-debug режиме приложение не стартует.
3. **Зачем `uv.lock`, если версии уже указаны в `pyproject.toml`?**
   В `pyproject.toml` указаны допустимые диапазоны, в lock-файле — точные версии всех транзитивных зависимостей. Lock даёт воспроизводимую сборку, а диапазоны оставляют возможность обновляться осознанно (`uv lock --upgrade`).

### Что изменилось бы в продакшене

- Секреты из secret manager (Vault, AWS/GCP Secret Manager), а не из `.env`.
- Отдельные настройки окружений, `DEBUG=false`, `SECURE_*` и HSTS, строгий `ALLOWED_HOSTS`.
- Postgres как управляемый сервис с бэкапами; приложение в контейнере за gunicorn/uvicorn.
- CI с ruff, pytest и проверкой миграций на каждый PR (в PRD это P1).
- Структурированные JSON-логи с request id (это B-05/M8).

### Заметка про локальное окружение

Порт 5432 занят контейнером `mep-postgres` (map-event-pipeline), поэтому в локальном `.env` указан `POSTGRES_PORT=5433`. В `.env.example` остаётся 5432.
